# Aphrosyne Atlas 路线图推进

一次只处理一个清晰、可验收的路线图阶段、批次或规划任务。路线图描述目标，当前代码和验证结果描述事实。

## 1. 选择权威路线图

不要绑定固定文件名，按以下顺序确定本轮依据：

1. 用户明确指定的路线图文件或批次。
2. 仓库 `AGENTS.md` 等当前项目规则声明的活动路线图。
3. 活动路线图直接引用的上层计划；只将其用于产品定位、长期边界和前置依赖。
4. 仍不明确时，只在 `docs/` 中查找名称或标题含 `roadmap`、`plan`、路线、阶段或里程碑的候选文档，先检查其定位、当前状态和更新时间，不扫描无关文档。

归档、legacy、已完成或被新路线取代的文档不是默认执行清单。若多个候选会导致不同实施范围，说明判断依据并请求用户选择；如果不会改变本轮范围，可自行选择并在计划中注明。

只更新本轮选定的活动路线图。不要因为某份上层计划仍存在，就自动修改或勾选它。

## 2. 判断任务模式

先根据用户动词和授权范围选择一种模式。

### 审阅与规划

适用于审阅、整合、重排、编写或修订路线图，以及用户明确说“不实施”。

- 可以读取代码和执行必要的只读验证来校正计划。
- 只修改用户授权的规划文件；不实施路线图中的代码任务。
- 完成文档与 Git 边界检查后停止，不自动进入第一批实施。

### 批次计划

适用于“规划下一批”“先给计划”“进入下一阶段”或目标批次尚不明确的请求。

- 核对现状并输出一个批次的实施计划。
- 计划至少包括目标、主要文件或模块、实施顺序、关键取舍、风险/降级、验收和建议提交边界。
- 用户确认前不编码。

### 批次实施

适用于用户明确要求“实施/执行”一个已有阶段或批次，或已经批准一份具体计划。

- “实施 R3”“按已确认计划执行”可视为对该既有范围的实施授权；先简要报告执行顺序，然后直接推进。
- “审阅 R3”“规划 R3”不构成编码授权。
- 若批次包含尚未解决且会改变结果的 Choice、产品决策或外部操作，先询问该必要选择；不要让它阻塞无关的客观修复。

## 3. 建立事实基线

采取任务动作前：

- 完整阅读仓库 `AGENTS.md`、选定路线图中相关阶段/批次的完整内容，以及其明确要求的直接依据。
- 记录当前分支、`HEAD` 和 `git status`，区分用户已有改动与本轮改动。
- 按“入口 → 调用链 → 配置 → 必要时扩大”的顺序核对代码，不重新进行无目的的全仓审计。
- 路线图复选框、报告、分支名和版本描述都不是完成事实；代码、产物和可重复验证优先。
- 若涉及 Next.js 行为，先完整阅读当前安装版本中与本批直接相关的 `node_modules/next/dist/docs/` 指南。若目标是安全升级，实施开始时还要核对当日官方安全公告与发布说明；升级后以新安装版本的本地文档重新验证，不能沿用旧版本假设。

处理已有工作树改动时：

- 无关改动保留并绕开，不清理、不覆盖。
- 与本批目标文件重叠且无法安全区分时，停止并请求用户确认。
- 收尾时用 `git diff --name-only` 和 `git status` 确认最终范围。

## 4. 计划与授权闸门

计划应直接继承选定批次已有的范围、非目标、前置依赖、风险和退出条件，不另造一条平行路线。

若发现以下情况，先回到计划或请求确认：

- 路线图与代码事实冲突，且会改变实施范围或完成判断。
- 前置批次未完成，必须先处理的内容超出“最小必要前置”。
- 需要明显改变视觉、功能、公开内容、内容模型或部署方式。
- 需要提交、推送、公开部署、创建远端资源、清理历史或其他额外授权。

普通实现细节可自行判断。用户已明确批准具体范围时，不重复索要确认。

## 5. 实施一个批次

- 严格遵守本批范围和非目标，不顺手实施下一批。
- 先处理共同根因，再迁移消费者；避免同一问题在多个位置分别打补丁。
- 保持改动小而可审查，每一步尽量可运行、可回退。
- 新发现但不属于本批的问题只记录到后续候选，不扩大当前任务。
- 如果根因迫使改动显著超出批准文件、产品范围或风险边界，停止实施并报告新的最小方案。
- 遵守静态优先、公开内容、资源路径、Blog/Knowledge 差异和现有视觉等项目约束；具体边界以 `AGENTS.md` 与选定路线图为准，不在 skill 中复制可能过期的阶段说明。
- 不默认提交、推送、部署、创建远端资源或执行破坏性 Git 操作。

## 6. 验证与状态更新

验证项目从选定批次的退出条件和 `AGENTS.md` 推导，不使用一套固定命令替代风险判断。

- 代码批次通常至少检查 lint、类型和 build；静态路由、资源或部署批次还要预览实际静态产物。
- 视觉和交互批次按路线图指定的页面、视口、主题、键盘、动效偏好和控制台矩阵验收。
- 纯文档规划默认检查 Markdown、链接、UTF-8、敏感信息和 Git diff；除非内容判断需要，不运行应用构建。
- 失败时先判断是本轮回归、既有基线还是环境限制，只修复本批授权范围内的问题。
- 最终结果区分“通过”“失败”“未执行”“环境无法验证”，不能把未测项写成通过。

只有全部退出条件都有代码和验证证据时，才在本轮活动路线图中标记完成。部分完成应保持未完成或标记进行中，并准确记录剩余项；不要更新无关路线图或上层计划。

## 7. 收尾

最终汇报：

- 完成或规划了什么。
- 修改的文件和关键取舍。
- 验证结果及未验证项。
- 已知限制、发现但未纳入的问题和下一批建议。
- Git 工作树状态，以及是否提交、推送或部署。

达到当前模式的停止条件后结束：规划任务不开始编码；批次任务不自动进入下一批。
