# Aphrosyne Atlas 阶段推进

以 `docs/atlas-plan.md` 为主路线图，一次只推进一个清晰、可验收的阶段或子阶段。

## 工作流

### 1. 定位

- 先读仓库 `AGENTS.md` 和 `docs/atlas-plan.md` 中当前阶段的完整内容。
- 结合 Git 状态、现有代码和构建结果判断真实进度；路线图复选框不是事实的唯一来源。
- 若工作涉及 Next.js，按 `AGENTS.md` 要求先阅读 `node_modules/next/dist/docs/` 中与本次改动直接相关的指南。
- 只检查当前阶段涉及的入口、调用链和配置，不无目的扫描整个仓库。

### 2. 计划

编码前在对话中给出一份与任务规模相称的实施计划，至少说明：

- 当前状态与本轮目标
- 准备修改的文件或模块
- 实施顺序和关键取舍
- 风险、降级行为与验收方法

若路线图与代码事实冲突，或存在会明显改变视觉、功能、公开内容或部署方式的选择，先列出问题并等待用户确认。普通实现细节可自行判断。

**用户确认计划前，不开始阶段编码。** 用户已经明确批准某个具体计划时，不重复索要确认。

### 3. 实施

- 严格限定在已确认的阶段范围内，不顺手提前实现后续阶段。
- 保持改动小而可审查，每一步尽量可运行、可回退。
- 静态化阶段优先保持现有页面和视觉基线；必须失效的服务器能力应提供明确的静态降级。
- 尊重工作树中已有改动，不覆盖或清理来源不明的用户修改。
- 不默认创建 GitHub 仓库、部署、提交或推送；只有用户明确要求时才执行这些外部或版本控制动作。

### 4. 验证与收尾

- 按本阶段风险选择验证，通常包括 lint、构建、静态产物预览和相关页面手动检查。
- 失败时先定位并修复当前改动造成的问题，再重跑受影响的验证。
- 只有代码与验收结果都支持完成时，才勾选 `docs/atlas-plan.md` 中对应项目；部分完成则准确记录剩余项。
- 最终汇报：完成内容、验证结果、已知限制、用户需要手动处理的事项，以及路线图中的下一步。

## 阶段边界

- 阶段 0–1：建立基线并完成静态导出，不进行首页删减或知识库开发。
- 阶段 2：准备并验证 GitHub Pages；创建仓库或公开部署必须由用户明确要求。
- 阶段 3：逐项决定旧功能去留，不把静态化自动等同于去个性化。
- 阶段 4–5：先确定知识库信息架构与样例，再批量迁移内容。
- 阶段 6：域名、镜像和长期维护不阻塞首版。

当用户指定阶段时，以用户指定为准；若它依赖尚未完成的前置条件，应明确指出并先处理最小必要前置工作。
