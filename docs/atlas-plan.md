# Aphrosyne Atlas 项目计划

> 将现有个人博客平稳迁移为可静态部署的个人内容站；先保留当前视觉与页面作为基线，确认 GitHub Pages 可用后，再进行功能删减并建设 Skyrim 知识库。

## 项目定位

Aphrosyne Atlas 是一个具有个人视觉风格的内容站，而不是单一用途的博客或文档模板。

- 首页继续承担个人表达和视觉入口的作用。
- Blog 保留原有文章、开发记录和随笔。
- Skyrim 知识库作为新的核心内容板块，采用更高效的分类、检索和阅读方式。
- 全站只维护一个 Next.js 项目、一套主题、一个部署流程和一个域名。

## 总体路线

```text
冻结当前视觉基线
        ↓
转换为纯静态导出
        ↓
部署并验证 GitHub Pages
        ↓
删减失去价值的动态功能
        ↓
整理内容模型与站点导航
        ↓
构建 Skyrim 知识库
        ↓
迁移首批文档并发布
```

## 执行原则

1. 静态化阶段不重新设计页面，不同时进行知识库开发。
2. 每个阶段都必须有可运行、可回退、可对照的结果。
3. 先解决部署约束，再决定哪些旧功能值得保留。
4. 内容是长期资产，页面组件和托管平台可以替换。
5. Blog 与知识库共用基础设施，但保持不同的信息架构。
6. 不把 `.env.local`、API Token、私人链接或个人文件提交到公开仓库。

## 阶段 1：转换为纯静态导出

目标：在尽量不改变当前视觉的前提下，让 `next build` 稳定生成 `out/`。

### 1.1 Next.js 输出模式

- [x] 按项目内 Next.js 16 文档，将 `output: 'standalone'` 改为 `output: 'export'`。
- [x] 移除仅为 Node.js 服务端部署使用的 `serverExternalPackages`。
- [x] 启用 `trailingSlash: true`，让各页面生成目录形式的 `index.html`，降低静态托管路由差异。
- [x] 保留所有已有静态页面和动态路由；动态路由继续提供 `generateStaticParams()`，并禁止未知参数在运行时生成。
- [x] 检查构建产物中首页、Blog、文章详情、Projects、About、Playground 和 404 页面是否存在。

### 1.2 GitHub Pages 子路径

项目仓库预计使用 `aphrosyne-atlas`，GitHub Pages 首次部署地址通常位于：

```text
https://<用户名>.github.io/aphrosyne-atlas/
```

- [x] 在生产构建时根据仓库名设置 `basePath`；本地开发保持空路径。
- [x] 优先只使用 `basePath` 处理子路径，不默认叠加 `assetPrefix`；只有构建验证证明 `_next` 资源路径仍有问题时再增加它。
- [x] 审计所有根路径资源：普通 `<img src="/...">`、CSS `url(/...)`、音频地址和客户端 `fetch('/...')` 不会像 `next/link` 一样自动补上 `basePath`。
- [x] 建立统一的公开资源路径辅助函数或构建期常量，避免在各组件里硬编码仓库路径。
- [x] 保证将来绑定自定义域名时，可以通过重新构建把 `basePath` 恢复为空，而不用修改页面代码。

### 1.3 图片、字体与浏览器 API

- [x] 为静态导出配置 `next/image` 的静态兼容方案；第一版优先使用 `images.unoptimized: true`，以后再做独立图片优化。
- [x] 检查 MDX 中的图片组件是否能正确处理 GitHub Pages 子路径（当前 MDX 源内容暂无图片；共享组件使用静态兼容配置）。
- [x] 使用本地思源黑体替代网络字体，GitHub Pages 构建不再依赖字体下载。
- [x] 检查 `window`、`document`、`localStorage`、Audio API 等浏览器能力只在客户端生命周期内访问。

### 1.4 现有 API 的静态兼容处理

此步骤只处理“能否导出”，不决定组件最终是否删除。

- [x] `/api/blog`：改为构建时生成的静态 JSON，或让页面直接使用构建期文章数据。
- [x] `/api/search`：暂时生成静态搜索清单，保持现有搜索界面可用。
- [x] `/api/github-contributions`：静态化阶段使用冻结数据或空数据降级，不在构建时依赖私有 Token。
- [x] `/api/hitokoto`：改为本地固定文案或静态文案集合，避免部署依赖第三方接口。
- [x] `/api/music`：不把临时音乐 URL 固化进构建产物；保留组件外观时显示静态元数据或“暂不可用”。
- [x] `/api/steam`：若当前没有页面使用，先停止参与导出；是否永久删除留到删减阶段决定。
- [x] 构建过程在没有 `.env.local`、`GITHUB_TOKEN`、`STEAM_API_KEY` 和 `STEAM_ID` 时也必须成功。

### 1.5 静态产物验收

- [x] 执行 `npm run lint`。
- [x] 执行 `npm run build`，确认生成 `out/`。
- [x] 使用本地静态文件服务器预览 `out/`，不能用 `next dev` 代替这项检查。
- [x] 从首页逐项点击内部链接，检查刷新深层路径、前进/后退、404 和主题切换。
- [x] 检查控制台没有 404、资源路径错误或 hydration 错误。
- [x] 对照阶段 0 截图，确认首页 Hero、Blog 列表和文章阅读页没有非预期视觉变化。

完成标准：关闭 Node.js 服务后，仅凭 `out/` 即可完整浏览网站；实时小组件允许降级，但页面主体、导航和视觉基线保持完整。

## 阶段 2：部署 GitHub Pages

目标：获得第一个公开可访问的 Aphrosyne Atlas 静态版本。

### 2.1 仓库准备

- [x] 创建 GitHub 仓库 `Aphrosyne-Atlas`。
- [x] 公开前检查提交历史和待提交文件，确认没有密钥、真实联系方式、私人网盘链接和不应公开的图片。
- [x] 更新 README：项目名称、当前定位、本地开发方式和部署说明。
- [x] 确认 License 对代码、原创文章和第三方素材的适用范围；必要时分别说明。

### 2.2 自动部署

- [x] 添加 GitHub Actions 工作流。
- [x] 使用锁文件执行 `npm ci`，随后执行静态构建。
- [x] 上传 `out/` 作为 Pages artifact，并由 GitHub Pages 官方部署 Action 发布。
- [x] 为工作流配置最小必要权限，部署环境使用 `github-pages`。
- [x] 在仓库 Pages 设置中选择 GitHub Actions 作为发布来源。

### 2.3 线上验收

- [x] 验证首页及 `_next` 静态资源能够从仓库子路径加载。
- [x] 验证直接刷新 `/blog/` 和至少两篇 `/blog/<slug>/`。
- [x] 验证头像、背景、Meme、代码高亮和 MDX 图片。
- [x] 验证桌面和移动端导航、搜索、主题切换与返回顶部。
- [x] 记录首次部署 URL、构建时间和已知降级功能。
- [x] 暂不绑定自定义域名；先观察 GitHub Pages 的真实访问效果。

完成标准：通过全新浏览器会话访问公开 URL，可以完成“进入首页 → 浏览 Blog → 打开文章 → 使用搜索”的基本流程。

## 阶段 3：删减与整理旧站

目标：在已有线上基线的前提下，减少无维护价值的功能，同时保留 Aphrosyne Atlas 的个性。

每个项目单独判断，不在静态化阶段一次性清空：

- [x] 音乐播放器与 FFT：删除、改为纯本地音频，或保留为独立展示。
- [x] GitHub Contributions：删除、改为静态快照，或改成跳转链接。
- [x] Steam：删除 API，只保留个人链接，或完全移除。
- [x] Hitokoto：使用本地语句集合或删除。
- [x] Status：改成本地配置或删除远程 Gist 依赖。
- [x] Clock、Meme、Playground：根据个人喜好保留，不因“知识库效率”自动删除。
- [x] Projects：完成、归档或从主导航隐藏。
- [x] About 与社交链接：替换占位内容并完成公开信息检查。
- [x] 将首页 12 列 Dashboard 布局集中配置，并提供本地可视化工作台用于拖拽、调节与导出布局。
- [x] 删除确定不再使用的 API Route、依赖、环境变量和 Docker/VPS 配置。
- [x] 再次执行静态构建和线上回归测试。

完成标准：站点不依赖自有服务器和私有 API；保留下来的功能都具有明确价值，且没有为了“纯净”而牺牲首页的核心视觉特色。

## 阶段 4：设计知识库信息架构

目标：先确定内容模型和导航，再开始批量迁移文档。

### 4.1 路由与目录

建议初始结构：

```text
src/content/
├─ blog/
└─ knowledge/
   ├─ guides/
   ├─ fixes/
   ├─ experiments/
   └─ reference/

src/app/
├─ blog/
└─ knowledge/
```

- [x] 将现有 Blog 内容移动到独立目录，同时保持旧 URL 可用或提供迁移方案。
- [x] 知识库使用 `/knowledge/` 路由，避免整个站点被限定为 Skyrim 单一用途。
- [x] 确定使用英文稳定 slug，并允许中文标题独立变化。
- [x] 设计移动端知识库导航，不把桌面三栏布局简单压缩到手机宽度。

### 4.2 文档元数据

首版字段建议：

```yaml
---
title: Engine Fixes 配置参考
type: guide
status: verified
game_version: Skyrim SE 1.6.x
pack: null
last_verified: 2026-09-04
tags:
  - Engine Fixes
  - 配置
---
```

- [x] 明确 `type`、`status` 和版本字段的允许值。
- [x] 区分“最后编辑时间”和“最后验证时间”。
- [x] 支持关联工具、相关文档和来源链接。
- [x] 对 `needs-review`、`outdated` 等状态提供明显但不过度干扰阅读的提示。
- [x] 内容解析不使用 `new Function` 执行元数据，改为明确、可校验的 frontmatter 方案。

### 4.3 两种阅读模式

- [x] Blog 继续按时间、摘要和标签组织。
- [x] Knowledge 按分类、版本、状态和关联关系组织。
- [x] 两者共用排版、代码高亮、主题和基础文章组件。
- [x] Knowledge 增加左侧分类导航、正文区和右侧目录。
- [x] 首页保持全屏 Hero；Hero 下方 Dashboard 增加知识库主入口和最近更新。

完成标准：无需迁移全部文档，也能通过一份示例文档验证路由、元数据、导航和响应式布局。

## 阶段 5：全文搜索与首批内容迁移

目标：完成“打开网站 → 搜索问题 → 找到记录 → 看清适用版本与验证状态”的闭环。

- [x] 将搜索范围从标题和摘要扩展到正文、小标题、标签和版本字段。
- [x] 搜索索引在构建期生成，浏览器端查询，不依赖服务器 API。
- [x] 全局搜索支持“全部 / 知识库 / Blog”范围过滤。
- [x] 验证中文、英文、Mod 名称缩写和混合关键词的检索效果。
- [x] 从 Skyrim 文档库选择 3～5 篇代表性内容，而不是一次性全部搬迁。
- [ ] 优先迁移：一篇完整教程、一篇问题汇总、一篇实验记录、一篇图片较多的长文。
- [x] 统一图片路径和文件命名，修复 Windows 反斜杠、空格路径及非标准 Markdown 图片尺寸语法。
- [x] `personal/`、私人网盘和不适合公开的内容不进入网站构建。
- [ ] PDF 作为可选下载或 Release 资产处理，不与 Markdown 正文重复维护。
- [x] 对游戏截图、引用内容和第三方资料补充来源与版权说明。

完成标准：公开站点上至少有 3～5 篇可搜索、可分类浏览、状态明确的真实知识库文档。

## 阶段 6：托管扩展与长期维护

此阶段不阻塞首版发布。

- [ ] 评估并绑定自定义域名。
- [ ] 使用相同 `out/` 产物测试 EdgeOne Pages 等静态托管平台。
- [ ] 如需中国大陆节点，再单独评估 ICP 备案和 OSS/COS 静态托管。
- [ ] 为死链、构建失败和过时文档建立低维护成本的检查流程。
- [ ] 根据真实使用需求决定是否增加离线 ZIP、PWA、PDF 导出或 Issue 勘误入口。

## 当前最近一步

下一轮只执行阶段 0 和阶段 1：

1. 建立旧版基线。
2. 改成 `output: 'export'`。
3. 处理 GitHub Pages 子路径和静态图片。
4. 为现有 API 提供静态兼容降级。
5. 在本地完整验收 `out/`。

在 `out/` 通过本地验收之前，不开始删减首页，也不开始开发知识库页面。
